# x86-64 backend: what is ported and what remains

Flapjack's Lean port added an x86-64 backend after the RISC-V and ARMv8 ones.
This note records which parts of HOL's x64 backend have a Galette
counterpart, and what a complete port still needs.

## Ported (definitions only)

| HOL script | Galette file | Status |
| --- | --- | --- |
| `cakeml/compiler/backend/x64/x64_configScript.sml` | `theories/cakeml/compiler/backend/x64/x64_config.v` | all definitions (`x64_names`, `x64_backend_config`), tagged |
| `cakeml/compiler/backend/x64/export_x64Script.sml` | `theories/cakeml/compiler/backend/x64/export_x64.v` | all definitions (`startup`, `ffi_asm`, `windows_ffi_asm`, `export_func`, `export_funcs`, `x64_export`), tagged; the SML-spliced `ffi_code`, `windows_ffi_code` and `entry_point_code` are untagged, as for ARMv8 |

These two scripts do not depend on the L3 machine model, so they compile
against the existing port.

## Remaining

1. **L3 x86-64 model** (`HOL/examples/l3-machine-code/x64/model/x64Script.sml`,
   11,473 lines, L3-generated). The ARMv8 model is produced by
   `scripts/l3-to-rocq/` (`regen-arm8.sh`); the x64 driver, header and patch
   are work in progress and are not committed.

   - `gen.sml` now handles constructor patterns with literal subterms (and
     nil patterns) by match-based conditions and bindings, and ascribes the
     type of every `ARB`. With the `binary_ieee`/`machine_ieee`/integer
     mappings below, generation of `x64Script.sml` completes with **no**
     failures (down from 24). Regenerating `arm8.v` changes only the added
     `ARB` ascriptions and two alpha-renames of a bound `flags` variable
     (to `flags'`, because `flags` is now a reserved name); no definition
     changes, so the generator changes are conservative.
   - The generated `x64.v` does **not** compile yet: Coq reports unresolved
     implicit arguments (`Inhabited word8`, `Decision` on word equalities)
     inside the ~160 KB `x64_decode` term, although the same instances resolve
     in isolation. The term needs to be split into smaller definitions (or
     generated as a match-based dispatch) before the model can be committed.
   - `binary_ieee.v` now ports the `flags` record and `clear_flags`,
     `invalidop_flags` and `dividezero_flags`; `machine_ieee.v` has
     `*_with_flags` stand-ins; `gen.sml` maps the `binary_ieee` types and
     `int_div`/`int_quot`/`int_exp`/`int_mod`/`int_rem`. The stand-ins are
     still `ARB`, so a *faithful* x64 FP proof needs `binary_ieee`'s
     real-valued semantics and the `*_with_flags` definitions, which are not
     ported.

2. **x64 step** (`x64_stepScript.sml`, 1,852 lines): `NextStateX64`, the
   fetch/decode/run wrapper and the memory read/write helpers.

3. **x64 target** (`x64_targetScript.sml`, 273 lines): `x64_next`, `x64_ok`,
   `total_num2Zreg`, `x64_ast`, `x64_encode`, `x64_enc`, `x64_config`,
   `x64_proj`, `x64_target`, and the `asmLib.target_asm_rwts` rewrites.

4. **Encoder correctness** (`encoders/x64/proofs/x64_targetProofScript.sml`,
   1,377 lines): `x64_encoder_correct`. The FP/SSE instructions make this
   proof depend on the faithful `binary_ieee`/`machine_ieee` port, so item 1
   is a prerequisite, not just bookkeeping.

5. **Integration**: `pancakeX64BackendConfig`, `panToTarget` instantiation
   and the driver's `--target=x64` branch, plus parity fixtures.

The x64 machine model is an L3 model, so the caveats in `docs/SOUNDNESS.md`
for the L3 RISC-V and ARMv8 models apply to it too, in a stronger form: the
L3 x86-64 model is a small subset of the architecture and is unrelated to
hardware or to any vendor specification.
